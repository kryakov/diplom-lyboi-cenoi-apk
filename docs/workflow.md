# Регламент разработки (Workflow)

Документ фиксирует правила совместной работы над проектом «Диплом любой ценой». Соблюдение этих правил обязательно для всех участников команды.

---

## 1. Базовые принципы Git

1. **Защита ветки `main`:**
   * Прямые коммиты и пуши в `main` строго запрещены.
   * Любые изменения попадают в `main` исключительно через Pull Request (PR).
2. **Правило единицы работы:**
   $$\text{1 задача} = \text{1 Issue} = \text{1 ветка} = \text{1 PR}$$
3. **Именование веток:**
   * Новая функциональность: `feature/<модуль>-<что>` (например, `feature/combat-projectile`, `feature/rooms-level1-json`).
   * Исправление багов: `fix/<модуль>-<что>` (например, `fix/player-diagonal-speed`).
   * Документация: `docs/<что>`.
4. **Оформление PR:**
   * PR создается строго в ветку `main`.
   * В описании обязательно указывать связь с задачей: `Closes #N` (где `N` — номер карточки Issue).
5. **Слияние (Merge):**
   * Вливать изменения в `main` имеет право **только тимлид**.
   * Используется исключительно стратегия **Create a merge commit** (Squash and merge запрещен, чтобы сохранить персональный вклад каждого участника).
6. **Запрещенные команды:**
   * Категорически запрещены `git reset --hard`, `git rebase` и `git push --force` для любых веток, которые уже отправлены на GitHub.
   * Откат ошибочных изменений выполняется исключительно через `git revert`.
7. **Культура коммитов:**
   * Коммиты должны быть небольшими и логически законченными.
   * Сообщения коммитов информативны и написаны в едином стиле: `Добавлен класс Player`, `Исправлено движение по диагонали` (запрещены названия вроде «fix», «123», «asdf»).

## 2. Карта владения файлами (Code Ownership)

Каждый файл закреплен за конкретной ролью. **Править чужие файлы без явного согласования запрещено.** Если требуются правки или интерфейсы из чужого модуля — создайте Issue его владельцу.

| Роль | Владелец | Закрепленные файлы и папки |
|---|---|---|
**1. Тимлид** | Тимлид | `main.py`, `src/core/game.py`, `src/core/scene_manager.py`, `src/scenes/game_scene.py`, `README.md`, `requirements.txt`, `.gitignore`, `.github/**`, `docs/WORKFLOW.md` *(а также заглушки `menu_scene.py`, `end_scene.py` до передачи роли 7)* 
| **2. Архитектор** | Архитектор | `src/settings.py` (после дня 1), `src/core/state.py` (`GameState`), `docs/architecture.md`, `docs/FORMAT.md`, `tools/validate_data.py`, `data/levels.json`, схемы JSON в `data/` |
| **3. Уровни и комнаты** | Разработчик уровней | `src/systems/rooms.py`, `src/systems/level_loader.py`, `src/systems/room_view.py`, `src/systems/assets.py`, `data/rooms/**` |
| **4. Игрок и бой** | Разработчик боевки | `src/entities/player.py`, `src/entities/projectile.py`, `src/systems/combat.py`, `tests/test_player.py` |
| **5. Враги и боссы** | Разработчик врагов | `src/entities/enemy.py`, `src/entities/boss.py`, `src/systems/ai.py`, `data/enemies/**` |
| **6. Диалоги и сюжет** | Сценарист | `src/systems/dialogue.py`, `data/dialogues/**`, `docs/STORY.md` |
| **7. Интерфейс** | UI разработчик | `src/ui/**`, `src/scenes/menu_scene.py`, `src/scenes/end_scene.py` |
| **8. Звук, сборка и проверка** | Звукорежиссёр и тестировщик | `src/systems/audio.py`, `assets/music/**`, `assets/sounds/**`, `assets/AUDIO_CREDITS.md`, `release/**`, `docs/TESTING.md` |
| **Художник** | Claude Code | `assets/images/**`, `assets/manifest.json` (правятся только по Issue-запросу роли 7) |

### Общие контракты и договоренности:
* **Зависимости:** файл `requirements.txt` редактирует только тимлид.
* **Константы:** общие параметры меняются только через архитектора в `src/settings.py`.
* **Снаряды (`Projectile`):** базовый класс создается ролью 4 в первую очередь; разработчики врагов не реализуют стрельбу до слияния `Projectile` в `main`.
* **Пути к ресурсам:** все пути в коде строятся **от корня проекта**, а не относительно текущей рабочей директории (критично для стабильной работы PyInstaller).

## 3. Кольцо код-ревью (Review Ring)

Каждый PR должен получить минимум **1 Approve** перед слиянием. Проверка идет строго по цепочке:

$$\text{1 (Тимлид)} \longrightarrow \text{2 (Архитектор)} \longrightarrow \text{3 (Уровни)} \longrightarrow \text{4 (Бой)} \longrightarrow \text{5 (Враги)} \longrightarrow \text{6 (Сюжет)} \longrightarrow \text{7 (Интерфейс)} \longrightarrow \text{8 (Звук и сборка)} \longrightarrow \text{1 (Тимлид)}$$

* Тимлид (1) проверяет Архитектора (2).
* PR Тимлида (1) проверяет Звук/Сборка (8).
* PR Звук/Сборка (8) проверяет Интерфейс (7).
* PR Claude Code проверяет автор запроса (Роль 7).

### Чек-лист ревьюера:
1. PR ссылается на открытую карточку задачи (`Closes #N`).
2. В PR изменены **только** файлы, закрепленные за автором роли.
3. Код проверен локально: `python main.py` запускается без ошибок.
4. В изменениях отсутствует мусор (`__pycache__`, `.idea/`, `.DS_Store`, временные файлы).
5. Коммиты названы содержательно.
6. В ревью оставлен хотя бы **один содержательный комментарий или уточняющий вопрос** (преподаватель оценивает глубину ревью).

## 4. Порядок работы над задачей (10 шагов)

1. **Взять задачу:** Открыть вкладку Issues или GitHub Projects, назначить себя исполнителем карточки.
2. **Обновить `main`:** В GitHub Desktop нажать Fetch origin, затем Pull origin на ветке main.
3. **Создать ветку:** Current Branch $\rightarrow$ New Branch, название по правилам из раздела 1.
4. **Писать код:** Править только закрепленные за ролью файлы (раздел 2).
5. **Проверить локально:** Запустить python main.py и python -m unittest discover -s tests, убедиться, что ошибок нет.
6. **Закоммитить:** Заполнить Summary содержательным сообщением и нажать Commit to <ветка> (если написано Commit to main, остановиться и создать ветку).
7. **Опубликовать:** Нажать Publish branch (первый раз) или `Push origin` для публикации коммитов.
8. **Открыть PR:** Создать Pull Request в ветку `main`, указать в описании `Closes #N`, назначить проверяющего по кольцу.
9. **Пройти проверку:** При наличии замечаний исправить код в той же ветке, закоммитить и запушить. Дождаться Approve.
10. **Слияние:** Тимлид выполняет слияние (Merge commit). После этого переключиться локально на `main` и выполнить `Pull origin`.

---

## 5. Действия при нештатных ситуациях

* **Случайно изменен чужой файл:** В GitHub Desktop нажать правой кнопкой мыши по файлу $\rightarrow$ `Discard Changes`.
* **Возник конфликт с веткой `main`:** В своей рабочей ветке нажать `Branch` $\rightarrow$ `Update from main`. Разрешить конфликты вручную в PyCharm, закоммитить решение и сделать `Push origin`.
* **Сломался `main`:** Немедленно сообщить тимлиду. Откат выполняется тимлидом через `git revert` отдельным PR.
